# 发布 v0.5.0 上生产：edge 全线切 SSE 通路 + Telegram 通知启用

## 概要

本次 session 是**纯发布/运维**，没有改 hookploy 的功能代码。起点是本地 master 上有 4 个已合并但未 push 的 notify commit，同时用户不确定更早的 SSE 通路（v0.4.0）有没有上过生产。

核查后发现两件事叠在一起：SSE 改动虽然在 2026-08-05 发布了 v0.4.0，但**生产三台一直停在 v0.3.2 从没升级**，所以 SSE 通路和它带来的流断容忍在线上完全没生效；而 notify 的代码还没发布。于是一次性做完：`go test ./...` 全绿 → push master → 打 v0.5.0 tag 触发 GitHub Actions 发布 release → 按 `kb/notes/2026-08-05-edge-sse-migration-guide.md` 的顺序（先 main 后 edge，一台一台切）把三台升级到 v0.5.0 并把两台 edge 切到 `--transport sse` → 同时给 main 配上 Telegram 通知。

最终结果全部验证通过：main 日志显示两台 edge 均为 `transport sse`；经 SSE 通路跑了一次真实部署（condenser `dp_19fdcf584`）为 `succeeded`、日志完整回传、healthcheck 200；用户在 Telegram 收到 `main.started` 推送。

**迁移指南里唯一未实测的风险点被证伪了**——45s 心跳注释帧能否穿透 Cloudflare 此前只是设计推断（真机验证是在 ali 本机 loopback 上做的，没经过 CF）。切换后 7 分钟观察窗口断连 **0 次**；作为对照，gRPC 通路的基线是 24h 内 **1372 次**（切换前实测），同样 7 分钟窗口本应有约 8 次。这条 TODO（deploy workspace 第 1 条，起因是 07-29 vocalflow-rt `dp_19faeb11` 被断连误判 failed）随之关闭，「看到 failed 先核对各实例 digest」的过渡期 SOP 退休。

## 注意事项

- **secret 不进 iCloud repo 的做法**：deploy workspace 在 iCloud 里，bot_token 绝不能落 repo。采用的模式是 role 用 `stat` + `slurp`（`no_log: true`）从服务器本机 0600 dotfile 读回来注入模板渲染，role 自身**从不创建也不覆盖**该文件；文件不存在时模板的 `{% if %}` 让整个 `notify:` 块消失（= 通知关闭，配置依然合法）。非密的 chat_id 照常放 group_vars。这个模式可直接复用到其他「配置结构在 repo、值在服务器」的场景。
- **token 的传输路径**：`envops read-value --unsafe | ssh <host> 'umask 077; cat > <file>'`。值不出现在 argv、不落本地磁盘、不进 transcript。切忌 `echo '<token>' | ssh ...`。
- **升级顺序不可颠倒（先 main 后 edge）**：新 main + 旧 edge（gRPC）完全兼容；反过来旧 main 上根本没有 `/edge/session` 路由，新 edge 的 SSE 会吃 404 并持续退避重试（刻意不自动回退到 gRPC——静默切换会掩盖配置错误）。
- **降级有个坑**：v0.3.2 及更早不认识 `--transport` flag，unit 里还带着它就降 binary 会让 `flag.Parse` 失败、进程退出码 2，而 systemd 是 `Restart=always` → 无限重启循环、edge 永久 offline。正确顺序是先 `-e hookploy_edge_transport=grpc` 下发，确认 online，再降版本。
- **回退成本极低**：无 schema 变更、无持久化状态，单台回退就是 `--limit <host> --tags hookploy-edge -e hookploy_edge_transport=grpc`，秒级。而且两台 edge 一台 sse 一台 grpc 长期共存是安全的（`edgehub` 天然是合并视图），迁移期间不用为一致性强行同步。
- **验证的判据要选对**：「edge online」不是成功判据——gRPC 时代它也一直 online。真正的判据是**断连次数**。切换第一台时天然形成对照实验（切了的接近 0、没切的仍是 1000+ 量级），比任何单独数字都有说服力。
- **ansible 的 `--syntax-check` 不带 `-i` 会误报**：inventory 在 `ansible/inventory.yml`，不加 `-i inventory.yml` 会报 "Could not match supplied host pattern" 让人以为主机配置坏了。
- SSH 到 ali-hk-01 偶发在连接阶段被掐（本地代理出口问题，服务器侧正常），ansible 会直接标 UNREACHABLE。重试即可；持续失败可用 `ssh -J ali-hk-01 <host>` 跳板（AGENTS.md 07-30 条已记录）。

## 遗留问题

- **24h 级断连对照数据还没看**：迁移指南建议切完第一台观察 24h 再动第二台，本次按用户要求一次到位，只有 7 分钟窗口的数据（0 次）。建议次日跑一次 `ssh ali-hk-01 'journalctl -u hookploy --since "24 hours ago" --no-pager | grep -c disconnected'` 补上长窗口确认。
- **「终局验证」尚未自然发生**：即一次真实发版恰好撞上断连、main 日志出现 `disconnected, holding N execution(s)` → `resumed N in-flight execution(s)` 而 deploy 仍 succeeded 的三连。这是流断容忍的完整闭环，只能等它自然出现（本机 loopback 用 `ss -K` 已复现过，但没经 CF）。
- **CF zone 的 Network → gRPC 开关仍开着**：SSE 不需要它，但 gRPC 通路作为回退路径还留着，等正式下线时再关。
- **`hookploy_grpc_url` 变量名已名不副实**（现在 edge 走的是 HTTP 口，值与 `hookploy_main_url` 相同）。纯机械重命名，刻意没和本次迁移混在一个变更里。
- gRPC 通路的 deprecation 尚未排期；deploy workspace 的 adnanh/webhook 退役观察期也仍在挂着（与本次无关，但同属待清理项）。
