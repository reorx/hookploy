# 发布 v0.7.0（step timeout/retries）并升级生产，vocalflow-rt 接上拉取超时重试

## 概要

上一个 session（commit 4d5a541）实现了 step 级 `timeout:` / `retries:` 修饰符，发布与上线步骤留在 `kb/next-up.md`，本次照做。push master、打 `v0.7.0` tag，release CI 全绿。生产按 v0.7.0 的要求先 edge 后 main：tc、hh 两台 edge 先升，然后在 ali 上用新 binary 预检改名后的配置，再把 deploy 模板里 6 处 `healthcheck … retries: 10` 改成 `attempts: 10`，和 main 升级同一次下发，三台对齐 v0.7.0。之后给 vocalflow-rt 的 `image.pin` 加上 `timeout: 3m` + `retries: 2`，手动部署一次验证（`dp_1a0d6473`）succeeded。有一处偏离计划：next-up 写的是用事故那次的 digest 做验证，但线上早已前进到 `239f02f1`，用旧 digest 等于三台回滚一版，所以改用当前线上 digest。`defaults.timeout` 维持 10m。升级过程中发现 CLI status 对"edge 比 main 新"也标 `(outdated)`，已登记为 known issue。

## 注意事项

- **升级顺序没有固定规则，每个版本单独判断**：v0.6.0 是先 main 后 edge；v0.7.0 必须先 edge 后 main，否则 main 的版本门控会拒派给老 edge。deploy 仓库 group_vars 注释和 AGENTS.md 都改成了"因版本而异，先读部署手册"。
- **ansible role 的任务顺序藏着一个坑**：hookploy role 先解压 binary，后渲染模板并 `validate`。配置语法有硬切时，一旦 validate 失败，磁盘上就是新 binary 配旧配置，main 平时照跑，下次重启才起不来。这类升级先把新 binary 传到服务器 /tmp，对 `sed` 改好的现网配置跑 `validate`（本次同时确认了硬切双向生效），再跑 role。
- **验证部署用"当前线上 digest"，不用历史 digest**：用历史 digest 就是回滚。同 digest 重新部署时 `image.pin` 只要约 1.5s（`Image is up to date`），`compose.up` 不会 recreate，smoke 照跑，对线上没有扰动，但修饰符接线、版本门控放行、edge 认新键这几件事都能验到。
- **判断 edge 读的是新键还是旧键**：看日志里 healthcheck 的 `attempt 1/N`。N=10 说明 edge 读到了 `attempts`，N=5 说明它回落到了默认值。
- Web UI 登录用 `--data-urlencode "token=$(cat .admin_token)"`，不能用 `token@.admin_token`：文件末尾的换行会跟着发出去，登录处理不 trim，结果登录失败。
